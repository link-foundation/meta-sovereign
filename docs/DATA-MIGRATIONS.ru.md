# Миграции данных: версионируемая схема данных (languages: [en](DATA-MIGRATIONS.md) • [zh](DATA-MIGRATIONS.zh.md) • [hi](DATA-MIGRATIONS.hi.md) • ru)

Когда меняется форма хранимых данных (поле переименовано, идентификатор считается иначе, дата хранится как ISO-текст), данные, уже лежащие на диске, должны последовать за ней. meta-sovereign хранит вместе с данными **версию схемы** и выполняет **миграции** по порядку, автоматически, когда данные открываются на запись (R-Z17).

## Как работают версии

- Версия — одна связь в хранилище, `meta:schema`: `{ version, applied: [{ id, at, ms, changed }], app }`. `applied` — история (какая миграция, когда, сколько длилась, сколько связей изменила); `app` — версия приложения, которое записало.
- Хранилище без этой связи — **версия 0**: формы данных до появления версий. Пустое хранилище считается актуальным.
- `CURRENT_SCHEMA` (в `js/src/storage/migrations/index.js`) — версия, которую пишет эта сборка. Каждая миграция — модуль `js/src/storage/migrations/<NNNN>-<slug>.js`, переводящий данные с версии `NNNN-1` на `NNNN`.
- Одни и те же модули работают на **хранилище сервера** (`data.lino`), на **восстановленных резервных копиях** и на **хранилище в браузере** (веб-страница / режим GitHub Pages).

## Что видит пользователь

| Где                                                            | Что происходит                                                                                                                                                                                                                                                   |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `meta-sovereign serve` или любая команда с записью             | Если хранилище старее, оно сначала мигрируется (сервер начинает слушать только после этого). В журнале: `migration_started`, по одной `migration_step` на миграцию (`id`, `scanned`, `changed`, `ms`; только числа, никогда содержимое), затем `migration_done`. |
| `meta-sovereign migrate --store=<dir>`                         | Мигрирует сейчас и печатает те же строки.                                                                                                                                                                                                                        |
| `meta-sovereign migrate --store=<dir> --dry-run`               | Считает, что изменила бы каждая миграция; ничего не пишет и не берёт блокировку.                                                                                                                                                                                 |
| `meta-sovereign migrate --store=<dir> --status`                | Версия хранилища, сколько миграций ожидает, история.                                                                                                                                                                                                             |
| `/api/health`                                                  | `schema: { version, current }`.                                                                                                                                                                                                                                  |
| Команды только для чтения (`export`, `backup`, `cv-read`, ...) | Никогда не мигрируют. Старое хранилище читается как есть (об этом одна строка `schema_old_read_only`); читающий код понимает старые формы.                                                                                                                       |
| Резервные копии                                                | Архив записывает `schema: { version }`. Восстановление старого архива сначала мигрирует его связи в памяти, так что при сбое ничего не записывается; новее — отказ `BACKUP_TOO_NEW`.                                                                             |
| Синхронизация узлов (`/ws`, `sync-connect`, WebRTC)            | Узлы обмениваются версиями схемы. Если числа различаются, данные не передаются, обе стороны пишут `SCHEMA_MISMATCH` с обеими версиями; обновиться должна более старая сторона.                                                                                   |

### Хранилище из более новой версии: `STORE_TOO_NEW`

Если хранилище записано более новым приложением (его версия выше `CURRENT_SCHEMA`), приложение **никогда в него не пишет**: сервер не запускается, команда останавливается с сообщением «this store was written by a newer version; update the app». Открытие только для чтения тоже отклоняется, чтобы не прочитать данные неверно. Обновите приложение (или откройте хранилище тем приложением, которое его записало).

### Мало места на диске: `LOW_DISK`

Миграция только дописывает журнал, но место ей нужно. Перед началом свободно должно быть не меньше 10% размера `data.lino` плюс 256 МБ; иначе ничего не меняется, а приложение сообщает, сколько нужно и сколько свободно. Освободите место и запустите снова.

## Откат: как неудачная миграция отменяется без копирования хранилища

`data.lino` только дописывается, поэтому миграция отменяется обрезкой файла:

1. Перед первой миграцией журнал сбрасывается на диск, а его длина в байтах надёжно записывается в `migration.json`.
2. Во время миграции уплотнение (compaction) приостановлено (журнал только дополняется), а бинарный снимок `data.bin` не пишется.
3. После каждой завершённой миграции дописывается связь `meta:schema`, а `migration.json` сдвигается к новой длине. Остановка между двумя миграциями сохраняет первую.
4. В конце `migration.json` удаляется.
5. Если миграция выбросила ошибку или процесс умер и следующее открытие нашло `migration.json`: `data.lino` обрезается до записанной длины (fsync), `data.bin` удаляется (он пересоберётся из журнала), журнал удаляется (`migration_rolled_back`). То же открытие пробует снова. Если и тогда сбой — приложение сообщает `MIGRATION_FAILED` с идентификатором миграции, а хранилище остаётся прежним.

Второй копии хранилища не создаётся, память остаётся на уровне того, что хранилище и так держит (миграции видят связи пачками по 1000 копий).

**Хранилище в браузере** — снимок, сохраняемый целиком, откатывать там нечего: миграции идемпотентны, `meta:schema` сохраняется после каждой, а вкладка, закрытая посередине, выполнит эту миграцию заново с тем же результатом. Хранилище браузера от более новой сборки остаётся нетронутым (страница работает на временной копии и вызывает событие `ms-schema-too-new`).

## Как написать миграцию

Чек-лист:

1. **Модуль** `js/src/storage/migrations/<NNNN>-<slug>.js`, экспортирующий `id` (имя файла без `.js`), `from` (`NNNN-1`), `to` (`NNNN`), `description` и `async up(ctx)`. Добавьте импорт и запись в `MIGRATIONS` в `index.js` и поднимите `CURRENT_SCHEMA` до `to`. Без импортов `node:` и без сети: это чистое преобразование данных, оно должно работать и в браузере.
2. **Идемпотентность и только вперёд.** Повторный запуск `up` после сбоя должен давать тот же результат: вычисляйте целевую форму из сохранённых полей и записывайте только отличающееся (`ctx.putMany` пропускает уже равные связи и считает только настоящие изменения).
3. **Тест с фикстурой в старой форме**: постройте связи так, как их хранил прошлый релиз (см. `js/tests/migrations-email.test.js`; лучше выводить из того, что пишет текущий код), примените миграцию и сравните с тем, что сохранил бы текущий код.
4. **Тест идемпотентности**: запустите дважды (`runMigrations(store, { migrations, from: <старая> })`); второй запуск меняет 0.
5. **Счёт при dry-run**: та же фикстура через `migrate --dry-run` (или `runMigrations(..., { dryRun: true })`) сообщает число изменённых связей и ничего не пишет.
6. **Строка в документации**: добавьте строку в таблицу ниже и укажите, что нельзя восстановить из сохранённых данных (и что старые записи остаются читаемыми).
7. Читающий код продолжает принимать старую форму, пока миграция какое-то время не поработает в релизах (открытие только для чтения не мигрирует).

`ctx` даёт:

- `ctx.scan({ prefix, where, batchSize }, async (batch) => ...)`: копии подходящих связей пачками; `ctx.get(id)`.
- `ctx.putMany(links)` / `ctx.put(link)`: записать изменённые связи; `ctx.tombstone(id)`: удалить одну.
- `ctx.rekey(oldId, newId, { patch })`: записать связь под новым идентификатором, оставить связь `alias:<oldId>`, указывающую на неё, пометить старый идентификатор удалённым. Другая связь под `newId` никогда не перезаписывается (учитывается в `ctx.stats.conflicts`). `ctx.rekeyMany(pairs, { fields, children, refMap })` делает это для многих пар и затем одним проходом направляет записи `children`, перечисленные скалярные `fields` (например `replyTo`) и всё, что отображает `refMap(text)` (идентификаторы внутри более длинных), на новые идентификаторы. `ctx.resolve(id)` идёт по псевдонимам, так что ответ, реакция или членство в чате со старым идентификатором всё ещё находятся.
- `ctx.log(name, counts)`: строка журнала только с числами; `ctx.progress({ scanned, changed })`; `ctx.dryRun`.

## Миграции

| Id                       | Схема  | Что делает                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| ------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0001-email-threads`     | 0 -> 1 | Письма, прочитанные из сырого RFC 822 (IMAP, POP3, `.eml`, `.mbox`), получают ключ беседы R-Z5 (первый id из `References`, иначе `In-Reply-To`, иначе собственный `Message-ID`, иначе тема без префиксов), родителя, `messageId` / `references` / `inReplyTo` и `timestamp` как ISO-время; все письма получают ISO-время. Пересчитывается из сохранённых `rawHeaders` и `subject`. Нельзя восстановить из сохранённого: декодированный вид темы в encoded-word и идентификатор письма без Message-ID; они остаются как есть и читаются.                                                                                                                                                                                                                                                                                         |
| `0002-whatsapp-chat-ids` | 1 -> 2 | Чаты WhatsApp получают стабильный id R-Z9: номер E.164, JID группы, JID со связанным id или `name:<хеш>` для экспорта сохранённого контакта. Пересчитывается из сохранённых `chat`, `chatName` и `via`; сообщение, прочитанное со страницы, переезжает в `msg:whatsapp:<новый чат>:<ключ>` (старый id по-прежнему находится через `alias:`), а `chat`, tokens и ссылки `chat:whatsapp:<id>` следуют за ним. Нельзя восстановить из сохранённого: чат, прочитанный по заголовку страницы (номер не сохранялся), экспортный чат `unknown` без имени, настоящий id группового сообщения, сохранённого под JID участника, и счётчиковые id старых экспортов; они сохраняют свои id (их чат обновляется, где его можно вычислить) и остаются читаемыми. Число таких случаев пишется в строку журнала `whatsapp_chat_ids_unresolved`. |
| `0003-vk-reactions-docs` | 2 -> 3 | Реакции VK хранятся как эмодзи, а номер остаётся в `reactionId` (раньше был голый номер); документы VK-изображения и gif, сохранённые как `file`, получают вид `photo` / `gif` и `ext`. Пересчитывается из сохранённых `reactions` и сохранённого `raw`; реакция без эмодзи в VK остаётся числом, а сообщение без `raw` сохраняет свои вложения. Id сообщений и чатов, отправители и время не менялись (никакие id не переезжают). Число записывается в строку журнала `vk_reactions_docs`.                                                                                                                                                                                                                                                                                                                                     |

### Изменения форм, объявленные другими задачами (каждая добавит свою миграцию по этому контракту)

| Изменение                                                                                | Как ложится                                                                                                   |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| R-Z7: удаления единообразно `deleted: { at, by, reason }`                                | Скан связей с `deleted: true` или `deletedAt`; `ctx.putMany`.                                                 |
| R-Z10: идентификаторы сообщений Facebook / LinkedIn; Facebook `timestamp_ms` число в ISO | Идентификаторы через `ctx.rekeyMany` (псевдонимы сохраняют ответы и реакции); время через `scan` + `putMany`. |
| R-Z9: идентификаторы чатов WhatsApp из названий в стабильные                             | `ctx.rekeyMany` с `fields: ['chat']` и `refMap` для дочерних `chat:whatsapp:<id>`.                            |
| R-Z11: у элементов GitHub появляется `externalId`                                        | `scan` + `putMany`, по возможности из сохранённого URL / идентификаторов.                                     |

## `SCHEMA_REV` Telegram — другое

`SCHEMA_REV` в `telegram-layer.js` говорит, с каким слоем API Telegram чат был прочитан в последний раз; `telegram-repair.js` перечитывает чаты из сети при его смене. Миграция не должна обращаться к сети, поэтому это отдельный механизм: миграция меняет форму хранимого, а ремонт заново спрашивает у Telegram то, что умеет сообщить новый слой.
