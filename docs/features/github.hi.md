[Telegram फ़ीचर समर्थन मैट्रिक्स](../FEATURES.hi.md) पर वापस।

## दायरा और पहुँच

GitHub को संचार चैनल माना गया है: issue, pull request, समीक्षा टिप्पणियाँ, discussion, सूचनाएँ, उल्लेख और जवाब। Issue #5 ("Add GitHub support") issue, टिप्पणियाँ और pull request माँगता है, साथ में हर रिपॉज़िटरी को links स्टोर में उतारना। कोड `js/src/sources/github.js` और `github-check.js` में है; Rust सर्वर में GitHub एडाप्टर नहीं है।

आज हिस्से कैसे जुड़ते हैं:

- **इम्पोर्ट**: Connections पेज पर JSON अपलोड, पेज में पार्स, एक-एक link सेव। सर्वर के बिना चलता है।
- **लाइव पुल**: `POST /api/github/pull` और CLI `source-pull --source=github` एक बार में एक रिपॉज़िटरी (`owner`, `repo`) लेते हैं। इन्हें कोई पेज बटन या शेड्यूल नहीं बुलाता, इसलिए "इस रिपॉज़िटरी को सिंक करें" नियंत्रण नहीं है और रिपॉज़िटरी-पार इनबॉक्स भी नहीं।
- **लाइव पोस्ट**: `POST /api/github/post-comment` (पुष्टि टोकन के साथ) और CLI `github-comment` तब चलते हैं जब कॉल करने वाला `owner`, `repo` और issue संख्या देता है।
- **चैट कंपोज़र, ऑटोमेशन, re-engage**: सामान्य भेजने का रास्ता owner, repo या issue संख्या नहीं देता, इसलिए चैट से GitHub थ्रेड का जवाब "requires owner and repo" फेंकता है (नकली `fetch` से दोहराया)।
- **चैट से संपादन, हटाना, प्रतिक्रिया**: एडाप्टर को दी जाने वाली संदेश id संख्यात्मक टिप्पणी id की जगह `owner/repo#123` है और owner व repo नहीं दिए जाते, इसलिए ये कॉल गलत एंडपॉइंट पर जाती हैं या विफल होती हैं।
- **संदेश का रूप**: id `msg:github:<kind>:<owner/repo>#<id>`, चैट `owner/repo#<issue या PR संख्या>`।

पहुँच से बाहर: GitHub Mobile पुश सूचनाएँ, Copilot चैट, खुले रूप में Actions secrets, और जिसके लिए आधिकारिक ऐप चाहिए। संचार के लिए GitHub वेब इंटरफ़ेस में आम उपयोगकर्ता जो कुछ करता है, बाकी सब REST या GraphQL API से पहुँच में है।

नियोजित सुधार: GitHub भेजने/संपादन/हटाने/प्रतिक्रिया की id, owner/repo, समीक्षा-टिप्पणी एंडपॉइंट, सूचना इनबॉक्स, क्रमिक पुल और GraphQL से Discussions R-Z11 में कतार में हैं; पुल बटन और शेड्यूल R-Z8 में।

## संकेत

- **स्थिति**: समर्थित = उपयोगकर्ता के चलाए ऐप में शुरू से अंत तक काम करता है; आंशिक = टिप्पणी में बताई सीमा के साथ काम करता है (अभी चल रहा सुधार "सुधार जारी (R-Z<n>)" से चिह्नित है; फिर भी आंशिक गिना जाता है); असमर्थित = बना नहीं; पहुँच से बाहर = ऐसी क्षमता चाहिए जो केवल आधिकारिक ऐप में है।
- **पहुँच**: API = REST या GraphQL (एंडपॉइंट सहित); वेब = ब्राउज़र में github.com; आर्काइव = फ़ाइल इम्पोर्ट; पहुँच से बाहर = आधिकारिक ऐप चाहिए। यहाँ GitHub का सारा काम API से होता है; वेब ऐप कहीं इस्तेमाल नहीं।
- **आवश्यकताएँ**: [`REQUIREMENTS.hi.md`](../REQUIREMENTS.hi.md) की R-ID, जो इस फ़ीचर को पूरा करती हैं। "—" का अर्थ है कोई आवश्यकता-पंक्ति इसे नहीं ढकती। आवश्यकता-पंक्ति में "Done" का अर्थ यह नहीं कि फ़ीचर जाँचा जा चुका है।
- **जाँच**: सब कुछ केवल नकली (fake) के साथ परखा गया है (इंजेक्ट किया `fetch` / नकली ब्राउज़र)। यहाँ कुछ भी असली खाते पर नहीं जाँचा गया। "planned (R-Z<n>)" बाद की लहर के लिए कतारबद्ध काम है; इससे स्थिति नहीं बदलती।

## ज्ञात कमियाँ

1. चैट से जवाब, संपादन, हटाना और प्रतिक्रिया काम नहीं करते: एडाप्टर को गलत टिप्पणी id मिलती है, owner/repo नहीं, और कंपोज़र उन्हें देता नहीं। Planned (R-Z11)।
2. रिपॉज़िटरी-पार इनबॉक्स नहीं, सूचनाएँ या उल्लेख नहीं, क्रमिक पुल नहीं (हर पुल पूरा इतिहास दोबारा पढ़ता है)। Planned (R-Z11, R-Z8)।
3. पेज पर कोई लाइव नियंत्रण नहीं: "अभी सिंक", रिपॉज़िटरी चयनकर्ता, शेड्यूल या नई-गतिविधि बैज नहीं। Planned (R-Z8)।
4. सटीकता: issue/PR स्थिति, लेबल, समीक्षा-टिप्पणी का diff संदर्भ, Markdown रेंडरिंग, परमालिंक, प्रतिक्रियाएँ और अवतार नहीं दिखते।
5. Discussions केवल इम्पोर्ट किए डंप से; GraphQL से लाइव Discussions planned (R-Z11)।
6. टोकन प्रवाह: OAuth device flow नहीं, केवल एक खाता, UI में Enterprise बेस URL नहीं, 429 या `Retry-After` सँभाल नहीं, और classic बनाम fine-grained टोकन का मार्गदर्शन कम।
7. रिपॉज़िटरी क्लोन में आकार सीमा या बाइनरी जाँच नहीं और सभी रिपॉज़िटरी एक साथ क्लोन नहीं हो सकतीं।
8. किसी भी चीज़ को असली GitHub खाते पर नहीं जाँचा गया; सारे परीक्षण नकली से हैं।
