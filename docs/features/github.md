## Scope and access

GitHub is treated as a communication channel: issues, pull requests, review comments, discussions, notifications, mentions and replies. Issue #5 ("Add GitHub support") asks for issues, comments and pull requests, plus downloading every repository into the links store. Code lives in `js/src/sources/github.js` and `github-check.js`; the Rust server has no GitHub adapter.

How the pieces connect today:

- **Import**: Connections page, upload JSON, parsed in the page, saved link by link. Works without a server.
- **Live pull**: `POST /api/github/pull` and the CLI `source-pull --source=github` take one repository (`owner`, `repo`). No page button and no schedule calls them, so there is no "sync this repository" control and no cross-repository inbox.
- **Live post**: `POST /api/github/post-comment` (confirmation token) and the CLI `github-comment` work when the caller gives `owner`, `repo` and the issue number.
- **Chat composer, automations, re-engage**: the generic send path does not pass owner, repo or issue number, so replying to a GitHub thread from Chat throws "requires owner and repo" (reproduced with a fake `fetch`).
- **Edit, delete, react from Chat**: the message id handed to the adapter is `owner/repo#123` instead of the numeric comment id, and owner and repo are not supplied, so these calls hit a wrong endpoint or fail.
- **Message shape**: id `msg:github:<kind>:<owner/repo>#<id>`, chat `owner/repo#<issue or PR number>`.

Routes and what each gives:

Not accessible: GitHub Mobile push notifications, Copilot chat, Actions secrets in the clear, anything needing the official apps. Everything else a person does in the GitHub web UI for communication is reachable through the REST or GraphQL API.

Planned fixes: GitHub send/edit/delete/react ids, owner/repo, review comments endpoint, notifications inbox, incremental pull and Discussions via GraphQL are queued as R-Z11; pull button and schedule as R-Z8.

## Legend

- **Status**: Supported = works end to end in the app a user runs; Partial = works with the limit named in the notes (a fix being worked on now is marked "fix in progress (R-Z<n>)"; it still counts as Partial); Not supported = not built; Not accessible = needs a capability only the official apps have.
- **Access**: API = REST or GraphQL (endpoint named); Web = github.com in a browser; Archive = file import; Not accessible = needs the official apps. All GitHub work here goes through the API; nothing uses the web app.
- **Requirements**: R-IDs in [`REQUIREMENTS.md`](../REQUIREMENTS.md) that deliver the feature. "—" means no requirement row covers it. A requirement row saying "Done" does not mean the feature is verified.
- **Verification**: everything is tested only with fakes (injected `fetch` / fake browser). Nothing here was checked against a live account. "planned (R-Z<n>)" marks work queued for a later wave; it does not change the status.

## Known gaps

1. Replying, editing, deleting and reacting from Chat do not work: the adapter gets the wrong comment id and no owner/repo, and the composer does not pass them. Planned (R-Z11).
2. No cross-repository inbox, no notifications or mentions, no incremental pull (every pull re-reads the whole history). Planned (R-Z11, R-Z8).
3. The page has no live control: no "sync now", no repository picker, no schedule, no new-activity badges. Planned (R-Z8).
4. Fidelity: issue/PR state, labels, review-comment diff context, Markdown rendering, permalink, reactions and avatars are not shown.
5. Discussions only from an imported dump; live Discussions via GraphQL are planned (R-Z11).
6. Token flow: no OAuth device flow, one account only, no Enterprise base URL in the UI, no 429 or `Retry-After` handling, and guidance on classic vs fine-grained tokens is thin.
7. Repository clone has no size cap or binary check and cannot clone all repositories at once.
8. Nothing has been verified against a live GitHub account; all tests use fakes.
