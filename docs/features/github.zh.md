## 范围与访问方式

GitHub 被当作沟通渠道：issue、pull request、评审评论、discussion、通知、提及和回复。Issue #5（“Add GitHub support”）要求支持 issue、评论和 pull request，并把每个仓库下载进 links 存储。代码在 `js/src/sources/github.js` 和 `github-check.js`；Rust 服务器没有 GitHub 适配器。

目前各部分的衔接方式：

- **导入**：Connections 页面上传 JSON，在页面内解析，逐条保存为 link。无需服务器。
- **实时拉取**：`POST /api/github/pull` 和 CLI `source-pull --source=github` 一次处理一个仓库（`owner`、`repo`）。页面没有按钮、也没有定时任务调用它们，所以没有“同步此仓库”的控件，也没有跨仓库收件箱。
- **实时发送**：`POST /api/github/post-comment`（需确认令牌）和 CLI `github-comment` 在调用方给出 `owner`、`repo` 和 issue 编号时可用。
- **聊天输入框、自动化、再次联系**：通用发送路径不传 owner、repo 或 issue 编号，所以在聊天里回复 GitHub 线程会抛出 “requires owner and repo”（用假 `fetch` 复现）。
- **在聊天里编辑、删除、回应**：传给适配器的消息 id 是 `owner/repo#123` 而不是数字评论 id，也没有提供 owner 和 repo，所以这些调用会打到错误的端点或失败。
- **消息结构**：id 为 `msg:github:<kind>:<owner/repo>#<id>`，聊天为 `owner/repo#<issue 或 PR 编号>`。

## 图例

- **状态**：已支持 = 在用户运行的应用中端到端可用；部分 = 可用但有备注中所述的限制（正在进行的修复标为“修复进行中 (R-Z<n>)”，仍计为部分）；不支持 = 尚未构建；不可访问 = 需要只有官方应用才具备的能力。
- **访问方式**：API = REST 或 GraphQL（已写出端点）；网页 = 浏览器中的 github.com；归档 = 文件导入；不可访问 = 需要官方应用。这里所有 GitHub 功能都走 API，没有使用网页应用。
- **需求**：实现该功能的 [`REQUIREMENTS.zh.md`](../REQUIREMENTS.zh.md) 中的 R-ID。“—”表示没有需求行覆盖它。需求行写“Done”并不代表该功能已被验证。
- **验证**：所有功能都只用假数据（注入的 `fetch` / 假浏览器）测试过，没有任何功能在真实账号上检查过。“planned (R-Z<n>)”表示排入后续批次的工作，不改变状态。

## 已知缺口

1. 在聊天里回复、编辑、删除和回应都不可用：适配器拿到的评论 id 不对，也没有 owner/repo，输入框也没有传。已计划 (R-Z11)。
2. 没有跨仓库收件箱，没有通知或提及，没有增量拉取（每次拉取都重读全部历史）。已计划 (R-Z11, R-Z8)。
3. 页面没有实时控件：没有“立即同步”、仓库选择器、定时任务或新动态角标。已计划 (R-Z8)。
4. 还原度：不显示 issue/PR 状态、标签、评审评论的 diff 上下文、Markdown 渲染、永久链接、回应和头像。
5. Discussions 只能来自导入的转储；基于 GraphQL 的实时 Discussions 已计划 (R-Z11)。
6. 令牌流程：没有 OAuth 设备流程，只有一个账号，界面里没有 Enterprise 基础 URL，没有 429 或 `Retry-After` 处理，关于经典与细粒度令牌的指引不足。
7. 仓库克隆没有大小上限或二进制检测，也不能一次克隆所有仓库。
8. 没有任何内容在真实 GitHub 账号上验证过；所有测试都用假数据。
