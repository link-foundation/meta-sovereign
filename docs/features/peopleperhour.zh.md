## 范围与访问方式

Issue #12 对 PeoplePerHour 提出与 issue #4（Upwork）相同的要求，包括 JavaScript 和 Rust 两部分。需求行 R-T1..R-T22 全写着 “Done”，但 Rust 部分只是列表里的一个名字，JavaScript 部分建立在猜测的端点上。这里没有任何内容在真实 PeoplePerHour 账号上验证过。代码：`js/src/sources/peopleperhour.js`。

**端点未经验证，是猜出来的。** 下面所有 API 路径都是按惯例杜撰的，不是来自文档。

- **官方 API**：未能确认个人账号存在。搜索 PeoplePerHour 开发者文档只找到第三方爬虫，没有 peopleperhour.com 的页面，仓库自己的调研（issue #12）说开发者门户需要审批，所有端点路径均未验证。路径 `GET /projects/search`、`/workstreams`、`/workstreams/{id}/messages`、`/proposals/{id}/messages`、`/projects/{id}/proposals`、`/me/proposals` 以及探测 `GET /api/v1/me` 都是猜的。OAuth 授权和令牌 URL 同样未验证。应把整条 API 途径视为“可能不存在”。
- **浏览器中的网页应用**（`https://www.peopleperhour.com/`）：`WEB_UIS` 里没有条目（只有 vk、telegram、whatsapp、x、facebook、linkedin 和 upwork 有），所以浏览器发送器完全无法读取或发送 PeoplePerHour。这是现实可行的途径，却完全未构建。
- **归档导入**：JSON 信封和 Earnings CSV。PeoplePerHour 数据导出的真实结构未验证。
- **不可访问**：移动应用、PeoplePerHour 托管的视频或通话功能，以及托管资金释放流程。

收件箱拉取已完成：“立即获取”按钮和每 5 分钟的定时任务 (R-Z8)；24 小时缓存清理和令牌刷新尚未接通 (R-Z7)。

## 图例

- **状态**：已支持 = 在用户运行的应用中端到端可用；部分 = 可用但有备注中所述的限制（正在进行的修复标为“修复进行中 (R-Z<n>)”，仍计为部分）；不支持 = 尚未构建；不可访问 = 需要只有官方应用才具备的能力。
- **访问方式**：API = 是否存在尚未确认的 PeoplePerHour API（每条路径都是“猜的”）；网页 = 浏览器中的 PeoplePerHour 网页应用（未构建）；归档 = 文件导入；不可访问 = 需要官方应用。
- **需求**：实现该功能的 [`REQUIREMENTS.zh.md`](../REQUIREMENTS.zh.md) 中的 R-ID。“—”表示没有需求行覆盖它。需求行写“Done”并不代表该功能已被验证。
- **验证**：所有功能都只用假数据（注入的 `fetch` / 假浏览器）测试过，没有任何功能在真实账号上检查过。“planned (R-Z<n>)”表示排入后续批次的工作，不改变状态。

## 已知缺口

1. 个人账号可能根本没有 API，且每条端点路径都是猜的。现实可行的途径是网页应用，但它没有构建（没有 `WEB_UIS` 条目），所以聊天无法可靠地读取或发送 PeoplePerHour。
2. 从聊天发送会抛错，因为没有从聊天推出 workstream 或 proposal id；按 `roomId` 读取会悄悄返回空。
3. PeoplePerHour 的简历同步现在返回 `unsupported` 而不是成功（已修复，R-Z4）。没有 PeoplePerHour 的 CV 方案。
4. 没有提交 proposal，也没有项目搜索或消息的页面界面。
5. 服务器路由没有测试；24 小时缓存清理从不运行，刷新令牌未使用 (R-Z7)；收件箱拉取已完成，并用模拟服务器测试 (R-Z8)；issue #12 的 Rust 部分未完成。
6. 没有任何内容在真实 PeoplePerHour 账号上验证过；所有测试都用假数据。
