# Requirements — Issue #25 (R-N series)

This file extracts every requirement from
[issue #25](https://github.com/link-foundation/meta-sovereign/issues/25)
into a stable identifier table. Each row is referenced by
`docs/REQUIREMENTS.md`, the case study README, the solution plan, and
the changeset that PR #26 ships.

## Requirement table

| ID    | Source line in issue                                                                                                                          | Acceptance criteria                                                                                                                                                                                                          | Tests / evidence                                                                                                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-N1  | "It should be mobile first"                                                                                                                   | Default rendering targets a 360 × 640 dp viewport. The shell exposes a bottom-nav at compact widths (≤640 px), a navigation rail at medium (641-1023 px), and a permanent drawer at expanded (≥1024 px).                     | `js/tests/web-shell.test.js` smoke-renders at 320, 768, 1280 px and asserts the nav structure.                                                                       |
| R-N2  | "UI/UX should be in best possible way"                                                                                                        | Tap targets are ≥44 × 44 px (WCAG 2.2 AAA on touch); nav buttons are 56 × 56 px. Bottom-nav respects `safe-area-inset-bottom`. Visible focus ring on all interactive elements.                                               | Visual regression via Playwright screenshots; CSS includes `:focus-visible` rules; manual audit notes in `docs/UI-DESIGN-AUDIT.md`.                                  |
| R-N3  | "All user facing UI must be translated, not partially, but fully"                                                                             | No English literal renders when the active locale is non-English. The empty-inbox copy in `connection-guides.js` is routed through `t()`. Fallback chain only escalates to English when a key is genuinely missing.          | `js/tests/i18n.test.js` extended with a "no English literal leaks into non-EN dictionaries" assertion (string-equality between EN and non-EN values flagged).        |
| R-N4  | (translation) "for each separate service we should have item"                                                                                 | The new Connections list has one card per provider with: provider name (translated), description (translated), connection state badge (translated), and the "open detail" affordance.                                        | `js/tests/connections-screens.test.js` asserts every provider in `providerCatalogue` produces a card whose label and badge resolve via `t()`.                        |
| R-N5  | "External services connections should be on separate page like settings"                                                                      | A dedicated `Connections` view replaces the embedded provider list in Settings. Settings retains only app-level preferences (theme, language, archive defaults).                                                             | New `js/src/web/connections/` module; nav-items.js exposes a `connections` entry; `js/tests/web-shell.test.js` finds the entry.                                      |
| R-N6  | "design in the best way, so it will show if we connected or not"                                                                              | Connection state is one of `connected`, `not-connected`, `action-required`. Each state has a translated label and a colour token (green / neutral / amber).                                                                  | Snapshot test of `ConnectionsList` cards with each state.                                                                                                            |
| R-N7  | "if we are not connected we for each service we should be redirected to separate screen/page"                                                 | Tapping a "Not connected" provider navigates to `/connect/<providerId>` (a dedicated detail screen) — no inline form on the list.                                                                                            | `js/tests/connections-screens.test.js` asserts navigation handler is called with the correct `providerId`.                                                           |
| R-N8  | "make sure it is easy for user to get all required data, and it is clearly explained how to get them, so no separate instructions are needed" | Each provider in `providerCatalogue` declares a `setupSteps[]` array. Each step has `id`, `titleKey`, `bodyKey`, optional `actionKey`/`href`, and renders inside `ConnectionDetail`.                                         | `js/tests/connection-guides-templates.test.js` asserts every provider has at least one step and every step uses translation keys (no raw English in non-EN locales). |
| R-N9  | "The tutorial should be based on actual UI elements, meaning we should make darker everything except next click/tap/press"                    | The tutorial overlay cuts a transparent inset around the next click target (identified by a `data-tutorial-id` attribute) and dims the rest with a configurable mask (default `rgba(8,12,20,0.7)`).                          | `js/tests/tutorial.test.js` extended with a `findTutorialTarget()` helper test and a "renders four mask panels around target rect" assertion.                        |
| R-N10 | "user is guided first to service connections - he selects any service he likes and there he is guided on how to setup this specific service"  | The default tutorial sequence opens with a "Connect a service" step pointing at the Connections nav entry. After the user picks a provider, follow-up steps surface inside `ConnectionDetail` and walk through `setupSteps`. | New `tutorial.connections.title` / `.body` keys; sequence captured in `defaultSteps` in `tutorial.js`.                                                               |
| R-N11 | "make UI design similar to Apple glass with semi transparent UI"                                                                              | Top-bar, bottom-nav, drawer, modal cards, and tutorial card use a `--surface-glass` token (backdrop-filter blur 28px, saturate 180%) with a solid fallback when `prefers-reduced-transparency: reduce`.                      | `js/tests/web-shell.test.js` asserts the rendered DOM includes `.glass` / `.glass-strong` classes; CSS audit step reviews the fallback rule.                         |
| R-N12 | "Use Apple/Google/Microsoft design guidelines … use Chakra UI + React.js"                                                                     | The redesign adopts Chakra UI's design _patterns_ (responsive tokens, semantic spacing scale, accessible primitives) without taking a hard runtime dependency. The rationale is documented in `components.md`.               | `docs/case-studies/issue-25/components.md` records the trade-off; bundle size delta captured in PR description.                                                      |

## Open questions

None at the time of writing. The maintainer's "Use Chakra UI" line is
treated as guidance for design tokens rather than a hard runtime
dependency; if the maintainer wants the runtime swap as a follow-up,
a separate issue should track the bundle-size impact and the
`@emotion/react` peer-dep cascade.
