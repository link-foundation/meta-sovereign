# X user authentication and publication receipts

The X adapter previously resolved only a bearer `token`. It ignored legacy API key/secret and access token/secret fields, did not distinguish explicitly configured application credentials from user credentials, and returned any successful publishing response as a completed post. Three regression tests fail before the change: legacy credentials produce “X access token is required”, an app-only write is attempted, and a missing post receipt is accepted.

The universal adapter now accepts explicit `oauth1-user`, `oauth2-user` and `app-only` authentication modes, plus `auto`. OAuth 2.0 uses an already-issued user access token without requiring a client secret or access-token secret. OAuth 1.0a signs the final URL/query with Web Crypto HMAC-SHA1. Automatic selection chooses legacy mode when legacy credential fields are present and rejects incomplete legacy credentials instead of silently changing identities. Otherwise it selects the user access token, then the application bearer token. Explicit mode and per-request values override selection. The existing `token` option remains a user-token alias; a token's actual permissions are still determined by X.

Environment inputs are `X_AUTH_MODE`, `X_ACCESS_TOKEN`, `X_API_KEY`, `X_API_KEY_SECRET`, `X_ACCESS_TOKEN_SECRET` and `X_BEARER_TOKEN`. The constructor and operation options accept corresponding `authMode`, `token`/`accessToken`, `apiKey`, `apiKeySecret`, `accessTokenSecret` and `bearerToken` fields. `authStatus()` exposes configuration, selected mode, read-only state and missing field names without credential values. App-only mode rejects every write before HTTP and cannot pass a user identity probe. Public reads remain subject to X endpoint permissions.

`testConnection()` reads `/2/users/me` without publishing. `publishPost()` requires a returned post ID. `deletePost(id)` uses the public-post deletion endpoint and requires an explicit positive deletion receipt. A missing publication/deletion receipt is uncertain; a negative deletion receipt remains a refusal. Network failures and missing receipts never cause automatic publishing retries. Existing DM routing and deletion remain distinct from public posts; unsupported profile updates still report their actual limitation.

Optional `META_SOVEREIGN_X_DEBUG=1` or constructor `debug: true` diagnostics contain only method, authentication mode, response/error phase, numeric error status and uncertainty. They exclude credentials, authorization headers, destination IDs, draft text and provider error bodies. The default is off.

Primary documentation confirms the distinction between [X authentication modes](https://docs.x.com/fundamentals/authentication/overview), the user authentication required by [creation](https://docs.x.com/x-api/posts/create-post) and [deletion](https://docs.x.com/x-api/posts/delete-post), and [OAuth signature normalization](https://www.rfc-editor.org/rfc/rfc5849). The RFC's original example signature is incorrect for POST: [verified erratum 2550](https://www.rfc-editor.org/rfc/inline-errata/rfc5849.html#eid2550) supplies the corrected vector used in both runtime and browser regressions. Query duplicates, empty fields and form parameters participate in normalization; JSON bodies do not.

The final focused run passes **71 tests** with concurrency one, covering the new authentication/lifecycle cases and existing connectors, message parity, routing and send honesty. Changed-source ESLint, the production web build and `node examples/x-publishing-auth.mjs` pass. The real Chrome regression runs the universal source bundle without Node shims, verifies the corrected RFC vector, signs a mocked publication/deletion lifecycle and refuses app-only publishing with no request. It is included in the existing Chromium/WebKit CI manifest; the complete runtime/browser matrix is left to CI. No live credentials or external writes are used, and no visual UI changes are made in this step.

The downloaded upstream file matches the pinned inspected source byte for byte.

The raw failing/passing checks, browser/build/example/lint logs, primary documentation snapshots, pinned reference source and upstream report are preserved with verified per-file hashes in `data/x-publishing-auth.tar.gz`. This completes the shared X transport primitives, not the full issue: saved destinations, credential-mode controls in CLI/API/UI and complete provider lifecycle integration remain open in BC01–BC07.
