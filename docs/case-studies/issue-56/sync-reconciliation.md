# Bounded initial and reconnect reconciliation

Published `4bfeaf2c` sends live operations but never reads stored records on a new connection. An offline edit or deletion survives its owner's durable reopen while another peer keeps the old value indefinitely. Both minimal production regressions in `js/tests/sync-reconciliation-production.test.js` fail on that exact parent, with `Missing offline edit` and `Missing offline deletion`. Run `python3 -B experiments/issue-56/reconciliation-before.py` to reproduce; it restores the working peer module in `finally`.

Matching-schema JavaScript causal stores now advertise optional reconciliation sessions. Addressed hello replies let later clients discover an already-connected shared TCP/WebSocket hub. Each direction scans raw storage incrementally, including payload-free causal deletion markers, while excluding `secret:*` and `meta:schema` before selecting payloads. Ordinary live replication stays subscribed throughout. Existing merge clocks decide which concurrent edit or deletion survives; snapshots do not invent fresh owner writes or revisions.

A sender retains one detached record awaiting an acknowledgement per remote session. The recipient acknowledges only after mutation admission and its explicit persistence barrier succeed. The initial raw entry count bounds a scan even if live writes append more records. Sessions default to a maximum of 16 with a 30-second idle deadline; both limits are validated and bounded. Cancellation, invalid records, rejected sends and failed persistence release the blocked scan and report unfinished exchange. Completed-session history is capped at 256 entries. Frames retain the existing 4 MiB wire limit; oversized records fail explicitly rather than allocating an archive queue. This unit does not fragment oversized individual records or garbage-collect deletion clocks.

Schema refusal cancels reconciliation on ordinary connections; a foreign schema does not silence matching clients on shared hubs. Wrong-recipient packets are ignored before schema checks. A captured late callback cannot reopen a detached connection. Encrypted store decorators preserve the raw reconciliation capability and flush barrier without decrypting or transmitting private records. Optional content-free `reconcile-start`, `reconcile-complete` and `reconcile-failed` phases use the existing default-off browser debug channel.

Focused verification:

- Two exact-parent durable edit/deletion regressions fail before the change and pass afterward. Both verify a second actual file-store reopen, stale-packet refusal and text/binary consistency.
- Forty-five focused sync checks pass, covering acknowledgement backpressure, delayed and failed persistence, duplicate/stale/wrong-recipient packets, bounded scans, schema/hub isolation, explicit send failure, cancellation and real TCP text, TCP binary and mixed WebSocket clients. Nine encrypted-store compatibility checks also pass.
- One rebuilt native WebKit scenario passes with a genuinely absent peer retaining IndexedDB. On return, it receives offline creations, edits and deletions; the signaling server holds none of those records. Existing causal edits, receive isolation, three-peer reload, deletion, departure readiness and page-error checks pass in the same scenario.
- An independent Playwright MCP probe uses actual IndexedDB with separately bundled exact-parent and final sources. The parent retains stale deleted/edited records and misses the new record. The final sources pass deletion, edit, creation, private exclusion, durable reopen and stale-packet refusal with no reported errors. The fixture and browser are closed afterward.
