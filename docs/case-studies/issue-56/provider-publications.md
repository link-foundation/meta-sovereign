# Telegram formatting and VK wall publications

The existing VK adapter published only direct messages through `messages.send`. Reusing that path for a public-wall destination would select the wrong operation. Telegram's bot adapter ignored an explicit HTML format and converted a missing `message_id` to the successful-looking string `"undefined"`. Its transport also discarded the distinction between an explicit permission refusal and a lost or unreadable write response. Five initial regressions reproduce the missing publication methods, ignored format and false receipt; two further regressions reproduce missing delivery-outcome metadata.

VK now exposes separate `publishPost`, `deletePost`, `authStatus` and read-only `testConnection` methods. Publishing requires an explicit wall owner: positive for a personal wall, negative for a community. A DM chat target cannot accidentally become a wall. Community authorship defaults only for community walls, explicit personal authorship remains possible, and malformed identity flags are rejected before HTTP. A caller's stable `clientId` becomes the provider's deduplication `guid`; otherwise the adapter creates a UUID. The receipt retains owner ID, post ID and public URL. Deletion requires that owner/post pair and a positive provider acknowledgement. Missing receipts remain uncertain and do not initiate a retry.

Credential type is explicit (`user` or `community`, also `VK_TOKEN_TYPE`), with per-operation overrides. `VK_OWNER_ID` can supply a default wall owner. A community credential cannot select a personal wall. VK's actual permission and captcha errors survive unchanged: the adapter does not equate configured credentials or a successful identity read with verified publishing/deletion permission. The identity probe calls `users.get` or `groups.getById`, checks the returned identity and never publishes a test message. Its result explicitly leaves `permissionsVerified` false.

The current pinned [official VK schema](https://github.com/VKCOM/vk-api-schema/blob/333481bd082ad747d4873ef4a77f9247097eeef0/wall/methods.json) documents wall ownership, authorship, deduplication and deletion; its access-token annotation lists user tokens. Its latest repository commit is dated 2025-04-14, so that annotation alone is insufficient evidence to preemptively refuse all community-token requests in 2026. The current developer method page failed in fetch-based browsing and returned HTTP 500 / `Internal Server Error` in an independent Playwright browser at 21:50 UTC on 2026-11-09. The implementation consequently preserves actual provider refusals rather than claiming unverified permission or silently switching identity. No live VK credential was used to infer additional support.

Telegram's bot adapter now honors explicit `html` and `plain` formats and validates returned message IDs. Separate public publication/deletion methods retain the message/chat pair and require positive receipts. `getMe` verifies bot identity without claiming destination permission. Existing bot messaging, stickers and user-session selection remain available. Explicit formats also pass through the connected MTProto user account: HTML becomes text plus entities, and plain text keeps markdown characters literally. Without an explicit format, the composer's established Telegram markdown behavior remains unchanged.

The shared streaming HTML parser handles basic styling and aliases, nested text styling, links, spoiler, code/pre language, block quotes and custom emoji. It decodes entities, counts offsets in UTF-16 units and uses the existing bounded long-message splitter. It rejects unsupported or malformed markup, unsafe link schemes and excessive nesting before sending through the user path. This is an explicit regular-message formatter, not a claim that every newer Telegram rich-message construct is implemented. The [Bot API documentation](https://core.telegram.org/bots/api#html-style) supplies the wire formatting and receipt contracts; its raw snapshot is archived with this case.

Bot connection loss, unreadable successful responses, HTTP 408/5xx and missing acknowledgements now retain uncertain delivery metadata. Explicit API permission failures remain known refusals, including provider descriptions and retry-after information. Timeout handling stays with the existing request budget and read retry policy. Write failures do not trigger automatic publication retries. Generic transport errors omit potentially token-bearing URLs from their visible messages.

The focused run passes **73 tests** at concurrency one, covering both new provider lifecycles, HTML/plain formatting, the actual connected-user send path, existing account/formatting/connectors and X authentication/receipts. After the final ID/boolean validation hardening, the **17 directly affected publication tests** pass again; the six formatter checks also pass after the prototype-tag rejection hardening. Changed-file ESLint and the production web build pass. `node examples/broadcast-publications.mjs` runs both real adapter lifecycles against a fake transport with dummy credentials. A real Chrome regression bundles the universal source without Node shims, verifies both publication/deletion paths, HTML/plain parsing, deduplication and uncertain receipts, and closes its browser. The existing Chromium/WebKit CI manifest includes this regression. Full runtime/browser matrices remain in CI; no visual screen is changed in this step.

The reference broadcast README, CLI and provider modules were inspected without executing them or copying their implementation. A separate dispatch defect was reported as [konard/broadcast#4](https://github.com/konard/broadcast/issues/4), created 2026-11-09 21:38:24 UTC: documented `send`/`test` forms are consumed as message text, the test helper has no dispatcher call, and whole-string option choices reject a documented comma-separated list. The report includes dummy, dry-run reproduction commands, explicit static-analysis limits, workarounds and proposed mocked CLI regressions. Its raw body and current issue metadata are archived alongside the pinned source.

`data/provider-publications.tar.gz` preserves raw failing/passing logs, browser/example/build/lint evidence, primary documentation, the inspected reference files, source pins and upstream report, with verified per-file hashes. This is shared adapter work for BC01–BC06. Saved multi-target destinations, credential controls, lifecycle history and consistent CLI/API/UI integration remain unfinished; [PR 57](https://github.com/link-foundation/meta-sovereign/pull/57) remains draft.
