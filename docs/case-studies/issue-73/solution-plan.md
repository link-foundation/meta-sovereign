## Decisions and tradeoffs

**Tenant boundary.** A single store writer owns links, media, source credentials, event streams, and persistent provider workers. An origin boundary handles browser identity and preferences. A distinct process and volume handle server data separation. User-chosen provider endpoints also require a network boundary. The Compose template starts an egress policy before the tenant process and publishes the app only on the proxy's loopback port.

**Access.** A workspace is one user's personal profile. Operator provisioning generates an independent high-entropy owner key and storage key. This avoids an email or identity provider dependency for a first hosted deployment. The access key exchanges for a bounded, in-memory session, and the browser sends a host-only Secure and HttpOnly cookie. SameSite, Origin checks and a same-origin form policy protect write operations. Logout removes the session and closes associated live connections. A deployment that requires separate identities for multiple people inside the same workspace needs a different permission model across data, provider accounts and automations.

**Provider boundary.** Reuse the same cloud-capable provider APIs, server jobs and browser inputs. A browser on a user's device can submit exports and provider codes, while live operations that depend on placed credentials or a signed-in browser require that device. A remote Chromium and browser-viewer stack would require separate browser sandboxes, consent, download scoping, per-provider profiles, independent credentials and confirmation before provider-side writes. It cannot recover the user's existing browser sessions or OS contacts. The current workspace exposes the supported API and upload alternatives and reports the status of device actions explicitly.

**Portability and operations.** Compose is a starting point for a Linux VM, and the same command can run behind other privately connected TLS ingresses that enforce equivalent egress and storage isolation. An operator starts an isolated project from the same version for every owner. A process restart invalidates sessions. The backing volume plus that store's key is the recovery unit. The browser holds preferences and live UI state. It deliberately does not run a background mirror of private workspace data.

## Verification

- `node --test --test-concurrency=1 js/tests/cloud-workspace.test.js` covers configuration validation, HTTP access, Origin and Host checks, session isolation, cache policy and revocation of event and WebSocket streams.
- `RUN_BROWSER_E2E=1 E2E_BROWSER=chromium npm run test:e2e:cloud-workspace` opens a TLS-proxied workspace in two browser contexts and checks branding, sign-in, navigation, data across reloads and sessions, browser storage and logout. GitHub CI runs this test in Chromium and WebKit.
- `RUN_BROWSER_E2E=1 CADDY_BIN=/path/to/caddy node experiments/cloud-workspace-caddy.mjs` opens a workspace through Caddy. It signs in, previews and applies a vCard upload, and confirms the imported contact survives a browser reload. The fixture generates a temporary certificate and data directory.
- `bash docker/test-cloud-workspace.sh` starts two independent Compose projects from empty volumes, checks their session and data separation, checks private-network egress, and verifies that data persists and sessions expire on restart. The Linux container job runs the same smoke test.
- See [GitHub checks](https://github.com/link-foundation/meta-sovereign/pull/74/checks) for the broader repository matrix. The fixtures use synthetic data and independent storage.
