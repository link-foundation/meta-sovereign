# Issue #16 — Atomic requirements (`R-O*`)

The text of [issue #16](https://github.com/link-foundation/meta-sovereign/issues/16) is captured in
[`data/issue-16.json`](./data/issue-16.json). Each `R-O*` row below is
a single, testable requirement extracted from the issue body. The
canonical surface lives in
[`docs/REQUIREMENTS.md`](../../REQUIREMENTS.md) section
**O. Provider connection settings (issue #16)**.

| ID    | Requirement                                                                                                                                                                                                                                                                                                                                             |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-O1  | The "Try directly" probe for every catalogued provider must hit a URL that can plausibly succeed — either an authenticated endpoint when the user has supplied a credential, or a tokenless health endpoint when the provider exposes one. No probe may hard-code a URL that is guaranteed to return `404` or `400`.                                    |
| R-O2  | Each provider that requires a token must expose a probe URL **template** that interpolates the token (e.g. Telegram `https://api.telegram.org/bot{token}/getMe`, Meta `https://graph.facebook.com/v22.0/me?access_token={token}`). Templates live in `providerCatalogue` and are unit-tested.                                                           |
| R-O3  | The SPA must provide a text input (`<input type="text">` / `<input type="password">`) for every credential field a provider needs. Tokens, secrets, and similar values use `type="password"`; non-sensitive identifiers (e.g. WhatsApp `phone_number_id`) use `type="text"`.                                                                            |
| R-O4  | The SPA must provide a `<input type="file">` upload control wherever a provider supports an archive import (Telegram Desktop JSON, Facebook DYI ZIP, WhatsApp `.txt` export, …) so users can load archives without a CLI.                                                                                                                               |
| R-O5  | Where uploading a file is impractical (very large exports, copy-pasted snippets, mobile WebViews), the SPA must offer a paste `<textarea>` fallback that accepts the same archive content.                                                                                                                                                              |
| R-O6  | All provider connections must live on a single **Settings** nav surface (a new top-level view). It is the only place where credentials are entered, archives are uploaded, and probes are executed.                                                                                                                                                     |
| R-O7  | Each existing per-section guide (chat, operator, contacts, automation, patterns, replies, facts, audience, broadcast, outreach, profile, backup, status) must include a button or link to Settings → Connections, with copy that explains "you must connect first to see data here". The link must deep-link to the relevant provider card on Settings. |
| R-O8  | Credentials entered in Settings must be persisted as encrypted-at-rest `secret:*` links via `wrapSecretStore`. They must never be sent over the sync wire (the existing outbound filter and inbound drop on `secret:*` must be preserved and unit-tested).                                                                                              |
| R-O9  | Settings must allow the user to remove a stored credential (forget token) and to re-run the probe after every change.                                                                                                                                                                                                                                   |
| R-O10 | The probe outcome must use the existing `tryDirect` classifier (`http` / `cors` / `network`) and render a remediation hint that matches the classification — e.g. on `cors` it must surface the local-server help block from issue #10 (`R-M5..R-M8` is preserved).                                                                                     |
| R-O11 | The repository must include unit tests for: the probe URL templates, the Settings reducer / store interactions, the secret-store round-trip, and the per-section "Connect first" CTA wiring.                                                                                                                                                            |
| R-O12 | The repository must include an integration test that boots the in-process server, walks the Settings → store → probe path, and asserts the credential is encrypted on disk (round-trip via the existing `secret-store.test.js` style).                                                                                                                  |
| R-O13 | The repository must include an end-to-end Playwright test that loads the locally-built SPA in a real browser, opens Settings, types a fake token into the Telegram input, clicks "Try directly", and asserts the resulting status badge is one of `http`/`cors`/`network` (never the literal `404`/`400` shape from the bug).                           |
| R-O14 | The repository must include an end-to-end Playwright test that runs against the **deployed GitHub Pages URL** after the Pages workflow finishes, and exercises at minimum the Settings page render and a no-credential probe attempt. The test runs in CI in a job that is gated on the Pages deployment having succeeded.                              |
| R-O15 | A deep case study lives at `docs/case-studies/issue-16/` (this folder), with online research for additional facts and data.                                                                                                                                                                                                                             |
| R-O16 | The case study must enumerate all requirements from the issue (this file).                                                                                                                                                                                                                                                                              |
| R-O17 | The case study must propose possible solutions and a solution plan for each requirement (`solution-plan.md`).                                                                                                                                                                                                                                           |
| R-O18 | The case study must check known existing components / libraries that solve a similar problem (`components.md`, `external-research.md`).                                                                                                                                                                                                                 |
| R-O19 | All work must land in a single PR (#17) and iterate until every requirement is fully addressed.                                                                                                                                                                                                                                                         |
