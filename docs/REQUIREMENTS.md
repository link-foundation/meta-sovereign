# Requirements (languages: en • [zh](REQUIREMENTS.zh.md) • [hi](REQUIREMENTS.hi.md) • [ru](REQUIREMENTS.ru.md))

This document is the canonical, top-level list of requirements that
`meta-sovereign` is building against. It collects directives from
implemented issues and maintainer comments so later PRs can extend one
stable requirements ledger.

For iteration-by-iteration breakdowns of how requirements have been
satisfied, see the per-issue folders under
[`docs/case-studies/`](./case-studies/).
[`docs/ROADMAP.md`](./ROADMAP.md) is intentionally present as an empty
review ledger; R-J10 records the single-PR completion criterion.

Each requirement carries a stable `R-*` identifier so changesets, PRs,
and code comments can reference it.

## K. Hardening (issue #6)

The following requirements arose from
[issue #6](https://github.com/link-foundation/meta-sovereign/issues/6) —
"Improvements and hardening system from data loss or unauthorized
access". The full atomic list and traceability live in
[`docs/case-studies/issue-6/requirements.md`](./case-studies/issue-6/requirements.md);
the canonical surface is summarised below.

| ID    | Requirement                                                                                                                                              | State                                                                                                                                                                               |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-K1  | Messages are **never** physically deleted by default — even when the upstream reports a delete; the link is marked `deleted: { at, by, reason }`.        | Done: `markDeleted` / `softDeleteLink` in `js/src/storage/soft-delete.js`; `DELETE /links/:id` tombstones by default.                                                               |
| R-K2  | Deleted links are still queryable so the user can recover them.                                                                                          | Done: `?include=tombstones` (or `?showDeleted=1`) on `GET /links` and `GET /links/:id`; `isTombstone()` helper for client filtering.                                                |
| R-K3  | Physical deletion only on **explicit operator confirmation**.                                                                                            | Done: `purgeLink(store, id, { confirm: true })` throws if not confirmed; HTTP requires both `?purge=1&confirm=1`.                                                                   |
| R-K4  | Bulk purge takes a query and refuses to run without an explicit `confirm: true` flag.                                                                    | Done: `bulkPurge(store, predicate, { confirm: true })`; `POST /api/links/purge-tombstones` requires `{ "confirm": true }` in the body and accepts `idPrefix` / `olderThan` filters. |
| R-K5  | Soft-delete propagates over sync so peers converge on the same tombstones; `purge` does **not** propagate.                                               | Done: tombstones are regular `put` writes so the existing peer mesh replicates them; `purge` calls `store.delete` directly and is therefore local-only.                             |
| R-K6  | All provider adapters report upstream deletes as soft-deletes by default.                                                                                | Done by construction: no adapter calls `store.delete` on upstream-deleted messages; the only deletion entrypoint, `DELETE /links/:id`, is now soft by default.                      |
| R-K7  | At-rest encryption uses a per-vault **master key** (data-encryption key); the master key never touches disk in plaintext.                                | Done: `js/src/storage/vault.js` generates a random 256-bit master key and stores only AES-256-GCM-wrapped copies on disk.                                                           |
| R-K8  | The master key is unlockable through **multiple methods**: passphrase, PIN, passkey (WebAuthn `prf`), authenticator-app TOTP recovery code.              | Done: `addUnlock({ kind, secret, label })` accepts `passphrase`, `pin`, `passkey`, `totp-recovery`. The browser passes `prf` blobs straight in.                                     |
| R-K9  | Adding or removing an unlock method does **not** require re-encrypting data — each method holds its own wrapped copy of the master key.                  | Done: `addUnlock` / `removeUnlock` only re-wrap the existing master key, leaving on-disk ciphertext untouched.                                                                      |
| R-K10 | The vault is loaded into memory only after a successful unlock; locking zeroes the key.                                                                  | Done: `lock()` calls `Buffer.fill(0)` on the master key and clears the in-memory reference; `encrypt`/`decrypt` throw if not unlocked.                                              |
| R-K11 | Removing the **last** unlock method is refused so users cannot accidentally orphan their data.                                                           | Done: `removeUnlock` throws when called on the only remaining method.                                                                                                               |
| R-K12 | Losing all unlock methods means the user loses access to their data and must re-import from upstream services. There is **no** recovery backdoor.        | Done: documented in `vault.js` header + this row; the wrap-the-master-key design has no escape hatch.                                                                               |
| R-K13 | Export-to-file is encrypted by default; the user is warned in the envelope that they are responsible for storing the file.                               | Done: `exportEncrypted(store, { passphrase })` wraps `encryptBackup` and embeds a top-level `warning` field; `DEFAULT_WARNING` exported for translators.                            |
| R-K14 | Encrypted exports round-trip through `decryptExport` (and `decryptBackup`) using the same passphrase.                                                    | Done: both raw `encryptBackup` envelopes and the new wrapped form open with one call.                                                                                               |
| R-K15 | The CLI exposes `meta-sovereign export-encrypted --file=… --passphrase=…`.                                                                               | Done: `js/bin/meta-sovereign.js` `export-encrypted` subcommand + `vault init/add-unlock/remove-unlock/list-unlocks` subcommands.                                                    |
| R-K16 | The HTTP server exposes `POST /api/export-encrypted` returning the same envelope, gated on a passphrase from the request body or `MS_SECRET_PASSPHRASE`. | Done: `routes-mutating.js` `handleExportEncrypted`; refuses without a passphrase.                                                                                                   |
| R-K17 | A documented `purge-tombstones` HTTP endpoint and CLI surface so operators can clean up after an audit.                                                  | Done: `POST /api/links/purge-tombstones` + `meta-sovereign purge-tombstones` both demand explicit confirmation.                                                                     |
| R-K18 | Compile data into `./docs/case-studies/issue-6/` (deep analysis, online research, requirements list, solution plans, components/libraries survey).       | Done: `docs/case-studies/issue-6/{README,requirements,solution-plan,components,external-research}.md` + raw issue/comment JSON in `data/`.                                          |
| R-K19 | Update `docs/REQUIREMENTS.md` (this file) with the issue-#6 surface.                                                                                     | Done: this section.                                                                                                                                                                 |
| R-K20 | Plan and execute everything in a single PR (#7).                                                                                                         | Done: PR #7 lands the case study, soft-delete, vault, encrypted export, and CLI/HTTP surface together.                                                                              |
