# Connection recovery and foreground responsiveness

The live 2026-10-28 investigation found automation and draft reads repeatedly copying every record in the saved archive before filtering. A CPU profile showed these copies and garbage collection dominating request handling. Automation definitions, pending drafts, run history, saved lists/audiences and audience-sync metadata now pass their filter into the store, so only matching records are copied. The regression refuses unfiltered queries on these automation paths. HTTP/2 account event streams also omit HTTP/1 connection headers.

Read failures keep loading automatically. Shared view readers retry after 1, 2, 5, 10 and then every 30 seconds, without an attempt limit. Each reader has one pending attempt. Returning to a failed view or regaining connectivity can wake it immediately; unmounting removes view retry timers and ignores late responses. Shared in-flight reads remain coalesced until they complete, are explicitly cancelled or their server binding closes. The conversation directory keeps its existing continuous retry loop and last successful snapshot. Initial failures use the centered loading region; a failed refresh retains the content already on screen. Operator keeps its card and toolbar instead of adding error panels above them.

The unlocked app owns one durable outbox across all sections. Moving from Chat or Operator to Profile, Settings or another section does not suspend queued sends. A recovered local-server probe or event stream wakes network retries immediately. Every attempt retains its client ID and reply options; only a confirmed successful send removes the pending item. Additional Telegram accounts have separate outbox storage keys.

Connection history survives reloads. After a server or Telegram has connected, a temporary outage shows the global yellow Reconnecting badge and keeps the existing screen; it does not recommend first-time browser-only setup. **Settings → Connection recovery → Offer browser-only mode after connecting a server or Telegram** explicitly enables that offer. It defaults off. A new browser with no previous connection still receives setup guidance.

`e2e-recovery-browser.mjs` blocks the fixture server, queues a message, changes sections, restores the server and verifies exactly one send with the same client ID. It tests the browser-only setting, repeated read failures that recover without a button, and the chat toolbar's common center and control height. The tests use a temporary store and fake sender, never personal conversations.

[Rolling server upgrades](ROLLING-SERVER.md) keep the public listener active while the installed replacement warms up. Repeated `serve` commands use the private host control socket; failed replacements leave the working version available.

## Shared request recovery

Connection interruptions do not raise global error toasts, including when a background read uses POST. `request-policy.js` classifies the Telegram call registry by read semantics, alongside GET/HEAD and shared history/directory readers. HTTP connection errors, interrupted JSON bodies and explicit temporary provider failures remain pending and retry after 1, 2, 5, 10 and then 30 seconds, with no attempt limit. Concurrent consumers share one pending read and receive a complete decoded answer. Returning connectivity wakes pending requests immediately.

Settings, contacts, profiles, histories, provider panels and local-passcode status use this shared request layer. Existing event streams also reconnect when mounted during an interruption. A source that enters the browser’s permanent CLOSED state is recreated with bounded backoff until its owning view unmounts, including account-notification streams. Cached content stays visible, and recovery is represented by the existing global badge and the affected load's spinner. The read layer keeps retries separate from confirmed mutations; queued messages continue through the durable outbox with their original IDs. Explicit account, permission and unsupported-feature responses retain their owner-specific handling.

Images, video/audio, stickers and full-screen media retain their placeholders while interrupted loads retry automatically. Animated stickers and custom emoji recover failed lookups and bytes rather than retaining a failed cache entry. Downloads and copied images use the same request recovery through complete binary bodies. Avatars reconsider earlier missing-photo results when a server connection recovers. Loading never requires clicking a media retry control.

`request-recovery.test.js` checks prolonged failures, shared requests, fresh attempt deadlines, interrupted JSON, POST classification and cancellation. Request deadlines measure inactivity: receiving bytes renews them so a large, healthy transfer can continue, while a body that stops delivering bytes is retried. The focused recovery browser scenario covers temporary failures while the server remains Online, reads queued across sections, absence of transport error toasts, and exactly one queued message send. The media browser scenario restores failed bytes without a manual retry and verifies stable geometry. Full regression suites and browser/runtime matrices run in CI/CD.
