# Connection recovery and foreground responsiveness

The live 2026-10-28 investigation found automation and draft reads repeatedly copying every record in the saved archive before filtering. A CPU profile showed these copies and garbage collection dominating request handling. Automation definitions, pending drafts, run history, saved lists/audiences and audience-sync metadata now pass their filter into the store, so only matching records are copied. The regression refuses unfiltered queries on these automation paths. HTTP/2 account event streams also omit HTTP/1 connection headers.

Read failures keep loading automatically. Shared view readers retry after 1, 2, 5, 10 and then every 30 seconds, without an attempt limit. Each reader has one pending attempt. Returning to a failed view or regaining connectivity can wake it immediately; unmounting cancels its retries and ignores late responses. The conversation directory keeps its existing continuous retry loop and last successful snapshot. Initial failures use the centered loading region; a failed refresh retains the content already on screen. Operator keeps its card and toolbar instead of adding error panels above them.

The unlocked app owns one durable outbox across all sections. Moving from Chat or Operator to Profile, Settings or another section does not suspend queued sends. A recovered local-server probe or event stream wakes network retries immediately. Every attempt retains its client ID and reply options; only a confirmed successful send removes the pending item. Additional Telegram accounts have separate outbox storage keys.

Connection history survives reloads. After a server or Telegram has connected, a temporary outage shows the global yellow Reconnecting badge and keeps the existing screen; it does not recommend first-time browser-only setup. **Settings → Connection recovery → Offer browser-only mode after connecting a server or Telegram** explicitly enables that offer. It defaults off. A new browser with no previous connection still receives setup guidance.

`e2e-recovery-browser.mjs` blocks the fixture server, queues a message, changes sections, restores the server and verifies exactly one send with the same client ID. It tests the browser-only setting, repeated read failures that recover without a button, and the chat toolbar's common center and control height. The tests use a temporary store and fake sender, never personal conversations.
