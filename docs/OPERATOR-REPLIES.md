# Operator replies and unfinished work

The 2026-10-28 investigation found a shared adapter that rebuilt outgoing messages with only `chat`, `to` and `text`. This discarded reply targets, quotes and delivery options after the browser and HTTP route had accepted them. The adapter now preserves the supported send fields, including the stable client ID. A browser fallback that cannot retain those semantics fails visibly rather than posting ordinary text. Invalid reply IDs are refused before sending.

New Operator cards still require positive unread counts and the configured chat type. Once a card has been checked and opened, it is unfinished work until **Done** succeeds. Sending a reply, clearing a Telegram unread count, receiving an update from another device, refreshing, and moving between sections do not complete it. **Next** moves it to the queue's end. Opened work and postponed order survive reloads in the same tab, scoped to its selected Telegram account. The Operator badge counts this unfinished work plus unread candidates; Chat continues to report Telegram's unread messages. Changing the configured chat types can hide work without completing it.

Operator does not issue read acknowledgements when showing a card or sending a reply. Telegram's unread count may change independently of the Operator workflow; such a change is no longer treated as completion. Only Done invokes this app's history-read operation and releases the card after success. Reply targets belong to their chat, so Next cannot transfer one person's reply target into another conversation.

`serve` already enables verbose file logging by default. Workflow diagnostics now include client reply selection, send attempts/results, candidate checks, retained cards, Next and Done, HTTP send intent/result, and the Telegram send parameters after adaptation. They share the client ID, chat/account identifiers and reply message ID where available. Message bodies, quoted text, credentials and confirmation tokens are omitted. Logs remain in `<store>/logs/meta-sovereign.log` with rotation; `--quiet-logs` is the explicit opt-out.

`e2e-operator-replies-browser.mjs` runs the real browser, confirmation route, shared adapter and Telegram request builder against a fake transport. It verifies two reply sends, clears unread counts as sends complete, checks that cards stay put, postpones them, reloads, then completes them only with Done. It also verifies per-chat reply targets and the diagnostic records. Chromium and WebKit run this fixture without sending any personal messages.

Connection recovery belongs to the global header: a yellow Reconnecting badge replaces Online while existing event streams reconnect. The same state is visible in Chat, Operator and Profile, with no duplicate reconnecting bar inside conversations. Actual history and media loading indicators remain local to their content. The browser fixture checks these transitions and recovery in each section.
