# 路线图 (languages: [en](ROADMAP.md) • zh • [hi](ROADMAP.hi.md) • [ru](ROADMAP.ru.md))

## meta-sovereign 适合谁

meta-sovereign 在网上**代表一个人或一个组织**。一位所有者连接自己用来沟通的账号——Telegram、VK、WhatsApp、Facebook 和 Instagram、X、LinkedIn、电子邮件、GitHub、Upwork、PeoplePerHour 以及招聘网站——并在自己电脑上运行的一个应用中处理所有对话。数据始终属于自己：本地存储、加密备份、中间没有云。

同一个收件箱、联系人和自动化服务于四类工作：

- **个人**：与人保持联系，记住说过的话，各处保持同一份简历。
- **销售**：跨网络寻找并细分潜在客户，大规模地逐一联系，跟进，快速回复。
- **市场营销**：向受众群发，发布帖子，发展并了解社区。
- **用户支持**：所有来信进入一个队列，以社区或企业账号回复，常用回复和由事实组成的知识库。

本文件把每个场景对应到它的**关键路径**：今天能用什么、哪些是部分支持、下一步做什么。各网络的细节见 [`FEATURES.zh.md`](./FEATURES.zh.md) 和 [`features/`](./features/)；每条需求及其证据见 [`REQUIREMENTS.zh.md`](./REQUIREMENTS.zh.md)。

## 如何阅读状态

- **就绪**：在应用中端到端可用，并有测试覆盖。测试使用模拟服务；只有 Telegram 的消息显示另外以只读方式在真实存储上核对过（见下文“验证”）。
- **部分**：可用，但有该行所述的限制。
- **计划中**：尚未构建；按优先级列在“下一步”中。
- **不可能**：需要只有官方应用才有的能力，或本地应用没有的公共服务器。

## 下一步（按优先级）

以下各项都没有日期；开始工作时为每项分配需求编号。

1. **真实账号验证。** 在用户在场的情况下，用用户自己的真实账号把每个网络的关键路径各走一遍（目前只以只读方式核对过 Telegram 的显示）。在此之前，每行的含义是“已用模拟服务测试”。
2. **引导式登录。** Gmail 和 Outlook.com 的带刷新 OAuth、X OAuth、GitHub 设备流程以及引导式获取 VK 令牌，不再需要粘贴一小时有效的令牌。
3. **无需 webhook 的企业来信。** 在 API 允许的地方按计划拉取 Facebook Page 会话和 WhatsApp Cloud API 消息；明确说明哪些地方只有 webhook 才行。
4. **面向组织的团队模式。** 一个服务器上多名操作员，各自登录；分配聊天、内部备注、谁回复了、角色。
5. **销售管道。** 联系人上的阶段、跟进提醒和“今日到期”列表、交易金额。
6. **活动结果与同意。** 每个自动化和群发的报告（已发送、已回复、已退订、未知），并自动把“停止”之类的回复加入退订名单。
7. **更丰富的发送。** 在 VK、X 和电子邮件中回复、发送照片和文件（附件、已发送副本、签名）。
8. **发布。** VK 墙帖子、LinkedIn 帖子的完整生命周期（编辑、删除、媒体）、带媒体的 X 帖子。
9. **求职者。** 在已登录的浏览器中处理招聘网站的招聘者来信，在真实网站上运行简历计划。

仅由所有者完成、不由应用完成：发布 npm 包，在用户真实账号上核对网页选择器。

## 验证

每条关键路径都由使用模拟服务的测试覆盖。只有 Telegram 的消息显示另外在真实存储上核对过（只统计数量，只读）；没有从真实账号发送过任何内容。因此“就绪”表示“按文档化的 API 或网页应用可用”，而不是“已在真实网络上看到可用”。第 1 项将补上这一点。
