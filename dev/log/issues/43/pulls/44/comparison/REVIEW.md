## Runtime, dependency and security configuration

The JavaScript template's package identity, engine ranges and demonstration dependencies are not appropriate replacements for this application. The local Node/Bun/Deno matrix is retained. Deno explicitly maps the actual maintained Telegram package, and the shared CommonJS resolver preserves `Api.BinaryReader` compatibility. KaTeX's vulnerable version is upgraded; committed npm/Cargo locks are audited. Registry deprecation metadata is tested separately from vulnerability results.

Native lifecycle approvals are explicit and complete for the reviewed better-sqlite3, esbuild and node-pty packages in npm, Bun and Deno. Deno installs before testing; no global ignore-warning or trust-everything option is introduced.

Electron is additional product infrastructure absent from the templates. The deprecated builder-26 chains are removed with an exact builder-27 prerelease and its required configuration migration. Native packaging, ad-hoc macOS signing, artifact names, update feeds and all existing target formats must pass CI. The independently staged updater's published versions still require deprecated lodash.isequal. A separate scoped exact alias to lodash.isequalwith 4.4.0 removes that installed warning while preserving its two-argument comparator contract, verified against the actual installed updater cache. This is independently validated from the builder lock audit. Windows Deno's native cipher access violation is isolated by a bounded reproducer and avoided by selecting the existing WASM backend before the actual Telegram entry path; other runtimes retain their selection.

The Rust template's release registry helpers, crate/tag naming and changelog-fragment merger are reviewed as publishing policy examples. All three local Rust crates intentionally have `publish=false` (existing PR 40), so adding crates.io releases would introduce a new feature. Rust fmt, clippy, tests, docs, CodeQL and lock audit remain applicable and required. The product's single npm Changesets channel remains authoritative.

The Python template's `pyproject.toml`, Ruff policy and PyPI publisher assume a distributable Python package. This project ships JavaScript and Rust; Python files are maintenance tooling and do not form a PyPI release. Python source is analyzed by CodeQL and relevant lint tooling. Importing a Python registry/token would add an unrelated product channel.

CodeQL covers JS/TS, Python, Rust and Actions, with evidence excluded. Scheduled lock audits supplement PR dependency review. Dependency graph permissions/capability are preflighted; a missing administrator setting on main is an actionable failure, while an unauthenticated PR is not required to publish a package.

## Product boundaries and preserved features

DockerHub publishing/buildx-resilience helpers in the templates target their shipped container images. Meta Sovereign currently has a Dockerfile but no container-image publisher. Principle 13 therefore means using native architecture runners if such a channel is added; it does not require adding DockerHub credentials or a new release today. Existing desktop architecture runners are native.

JavaScript-first parity/generation and universal-app preview workflows belong to template demonstrations. Their data, Android/iOS examples, preview screenshots and parity snapshots are inventoried as context. This PR retains the real application's runtime matrix, complete Chromium and native WebKit manifests (41 suites after the message-history main merge), package cold-install smoke, desktop smoke and Pages deployment.

Formatting/secret/duplication ignores apply to immutable collected logs/reference sources. Maintained product source and reusable experiment scripts remain subject to applicable checks. Existing four-language product documentation, optional integrations, provider names, Telegram compatibility patch, desktop download catalogue and updater/release APIs are retained.

The 145 template regression files are read-only design references. Corresponding product cases use real temporary Git histories, injected API results, child-process probes, parser fixtures and actual CI packaging/browser/runtime execution. Template-specific package exports and generated-demo assertions are not meaningful product tests and are not imported as green checks.

Post-archive execution also validates configuration isolation: the JavaScript template's empty `bunfig.toml` lets default Bun discovery execute archived tests as host tests (F21). The product now sets the real Bun test root to `js/tests`, matching its complete maintained Node/Deno test tree. A finite owned sentinel regression proves both maintained inclusion and evidence/build exclusion. The pinned snapshot remains unchanged; the shared template fault is reported as JavaScript issue 269.


Final review also compares the template's already repaired release badge recognizer and argv-based commit writer. F22 repairs the host's older substring/manual-escaping implementations with exact generated badge identity and installed command-stream argument interpolation, verified by regression cases and real Git messages. Existing upstream issue 208 is closed; its complete evidence is retained. F23 collects external service contexts as well as workflow jobs, because CodeQL upload success and the separate findings-check conclusion differ.
